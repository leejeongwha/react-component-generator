# Commit 스킬

변경사항을 분석하고 컨벤션에 맞는 한국어 커밋 메시지를 작성한 뒤 바로 커밋합니다. 사용자의 별도 승인 없이 진행합니다.

## 커밋 메시지 컨벤션

```
<type>(<scope>): <한국어 요약>

[선택] 상세 설명 (변경 이유, 영향 범위 등)
```

### type 종류

| type | 사용 상황 |
|------|----------|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 코드 리팩토링 (기능 변화 없음) |
| `chore` | 빌드 설정, 패키지, 환경설정, 문서 등 |
| `style` | 코드 포맷, 세미콜론 등 스타일 변경 (기능 무관) |
| `test` | 테스트 추가·수정 |
| `docs` | 문서 작성·수정 |
| `perf` | 성능 개선 |

scope는 영향받는 모듈·컴포넌트 이름 (선택). 요약은 명사형 또는 동사 원형으로 끝냄.

**예시:**
- `feat(Button): 로딩 스피너 상태 추가`
- `fix(auth): 토큰 만료 시 리다이렉트 오류 수정`
- `chore: ESLint 설정 업데이트`
- `refactor(hooks): useUser 중복 로직 통합`

## 절차

### 1단계: 변경사항 파악

```bash
git status
git diff --staged
git diff
```

staged와 unstaged 변경을 모두 확인한다. 아직 staged가 없으면 unstaged 변경을 기준으로 진행한다.

### 2단계: 논리적 단위로 분류

변경사항을 읽고 **왜** 변경됐는지 파악한다. 하나의 커밋이 하나의 관심사(concern)를 담도록 분류한다.

- 새 기능 + 관련 버그 수정이라면 두 개 커밋으로 분리할지 검토
- 규모가 작고 서로 연관된 변경은 하나로 묶어도 됨
- 분리가 필요한 경우 사용자에게 알리고 순서를 제안

### 3단계: 커밋 실행

staged가 없으면 관련 파일을 `git add`한다. 파일을 개별로 추가하되, `.env`, 시크릿, 불필요한 빌드 결과물은 제외한다.

```bash
git add <파일 목록>
git commit -m "$(cat <<'EOF'
<type>(<scope>): <요약>

<상세 설명 (있는 경우)>

Co-Authored-By: Claude Sonnet 4.6 <noreply@anthropic.com>
EOF
)"
```

커밋 후 `git log --oneline -3`으로 결과를 확인하고 사용자에게 보여준다.

## 주의사항

- `.env`, 비밀번호, API 키, 인증서가 포함된 파일은 절대 커밋하지 않는다
- 커밋 전 항상 `git status`로 staged 파일 목록을 검토한다
- 변경사항이 없으면 커밋하지 않고 사용자에게 알린다
- `--no-verify` 같은 훅 우회 옵션은 사용하지 않는다
