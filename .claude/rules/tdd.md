> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**

# TDD Rule

## 프로젝트별 규칙 우선 조항

프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 명시되어 있으면 그것을 우선한다.  
이 파일은 프로젝트 규칙이 없을 때의 기본값(fallback)이다.

---

## 적용 기준

### TDD 필수 적용 대상

- **비즈니스 로직** — 조건 분기, 계산, 상태 전이
- **API / 서버 핸들러** — 요청 처리, 응답 형식, 에러 분기
- **유틸리티 함수** — 순수 함수, 데이터 변환
- **버그 수정** — 재현 테스트를 먼저 작성한 뒤 수정

### TDD 불필요 대상

- 타입 정의 (`*.d.ts`, interface, type alias)
- 설정 파일 (`vite.config`, `tsconfig`, `.eslintrc` 등)
- 순수 UI 컴포넌트 (로직 없이 props를 렌더링만 하는 컴포넌트)
- SQL / 마이그레이션 파일

---

## RED-GREEN-REFACTOR 사이클

### RED — 실패하는 테스트 먼저

1. 구현하려는 **하나의 동작**에 대해 테스트를 하나 작성한다.
2. **반드시 실행해서 실패를 눈으로 확인한다.** 실행하지 않는 RED는 RED가 아니다.
3. 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류나 import 실패면 테스트가 잘못된 것이다.

### GREEN — 최소한의 코드로 통과

1. 테스트를 통과시키는 **가장 단순한 코드**만 작성한다.
2. **YAGNI** — 테스트가 요구하지 않는 기능을 미리 구현하지 마라.
3. 신규 테스트와 **기존 테스트 모두 통과**하는지 확인한다.

### REFACTOR — 구조 개선, 동작 유지

1. 중복 제거, 이름 개선, 헬퍼 추출만 한다.
2. REFACTOR 중 새로운 동작을 추가하지 마라.
3. **Green을 유지**하며 리팩토링한다. 테스트가 깨지면 즉시 되돌린다.

### 반복

REFACTOR가 끝나면 다음 동작에 대한 RED로 돌아간다.

---

## 삭제 강제 규칙

테스트 전에 프로덕션 코드를 먼저 작성했다면 **삭제하고 RED부터 재시작한다.**  
"참고용"으로 주석 처리하거나 별도 파일로 보관하는 것도 금지한다.  
이미 작성한 코드가 아깝더라도 순서를 지키는 것이 원칙이다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트가 불필요하다" | 단순하면 테스트 작성 비용도 단순하다. 단순한 함수가 단순한 이유로 망가진다. |
| "나중에 테스트를 추가하겠다" | 구현 후에는 테스트가 코드를 검증하지 않고 코드를 따라 쓰게 된다. 나중은 오지 않는다. |
| "시간이 없다" | 버그 수정과 디버깅에 쓰는 시간이 테스트 작성 시간보다 길다. TDD는 속도를 높인다. |
| "이미 작성한 코드를 삭제하면 낭비다" | 순서가 틀린 코드를 기반으로 쌓는 것이 낭비다. 삭제는 재시작이지 손실이 아니다. |
| "프로토타입이라 TDD가 필요 없다" | 프로토타입이 프로덕션이 되는 순간 테스트 없는 코드가 남는다. 프로토타입도 동작을 검증한다. |
